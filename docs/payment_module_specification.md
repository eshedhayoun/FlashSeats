# Module Design Specification: Payment Module

## 1. Module Overview & Scope

- **Core Responsibility:** Handles external payment gateway integration via the Stripe Java SDK (Test Mode). Manages payment intent creation, processes client payment authorization requests, enforces client-side idempotency to prevent double-charging, processes incoming Stripe webhook events asynchronously, and reports transaction status to the order and hold modules.
- **Domain Position:** Phase 3 (Security & Payment Integration). Connects active seat reservations from Phase 2 with permanent financial persistence.
- **Explicit Boundary Limits:** Strictly forbidden from checking inventory stock counters directly (owned by catalog/hold), managing line ranks (owned by queue), creating final order records (owned by order), or generating PDF tickets (owned by notification).

---

## 2. Package Structure & Code Layout

The module follows standard package structuring under `com.app.payment`:

* **`controller`**: Contains REST controllers for client payment intent creation, frontend payment submission handlers, and incoming Stripe webhook endpoints.
* **`service`**: Contains business logic for Stripe SDK interaction, idempotency key validation, retry management via Resilience4j, and webhook signature verification.
* **`facade`**: Defines the public Java interface (`PaymentFacade`) and implementation (`PaymentFacadeImpl`) exposed exclusively to other backend modules (such as order).
* **`repository`**: Handles database persistence for transaction ledgers and payment event logs in PostgreSQL.
* **`model`**: Internal PostgreSQL relational entities for payment transactions, gateway request logs, and webhook history.
* **`dto`**: Immutable data transfer objects for payment intent requests, gateway response payloads, and webhook event payloads.
* **`event`**: Domain events published when payment attempts succeed, fail, or undergo asynchronous reconciliation.

## 3. Data Storage & Schema Design

### PostgreSQL Tables (Relational Audit Ledger)

#### Table: `payment_transactions`

| Column Name | Data Type | Constraints / Attributes | Description |
| :--- | :--- | :--- | :--- |
| `id` | `BIGINT` | Primary Key, Auto-increment | Unique internal transaction identifier. |
| `transaction_reference` | `VARCHAR(64)` | Unique, Not Null, Indexed | System-generated tracking string (e.g., `TXN-884912`). |
| `hold_token` | `VARCHAR(64)` | Not Null, Indexed | Associated seat reservation hold token. |
| `user_session_id` | `VARCHAR(255)` | Not Null | Guest session identifier. |
| `stripe_payment_intent_id` | `VARCHAR(255)` | Unique, Nullable, Indexed | External reference identifier returned by Stripe (e.g., `pi_3Mtw...`). |
| `idempotency_key` | `VARCHAR(64)` | Unique, Not Null, Indexed | Client-provided token ensuring single execution of payment charges. |
| `amount_cents` | `BIGINT` | Not Null | Transaction charge amount in smallest currency unit. |
| `status` | `VARCHAR(32)` | Not Null | Payment processing state (`INITIATED`, `PROCESSING`, `SUCCEEDED`, `FAILED`, `REFUNDED`). |
| `failure_reason` | `VARCHAR(255)` | Nullable | Text explanation or error code if gateway rejects payment. |
| `created_at` | `TIMESTAMP WITH TIME ZONE` | Not Null | Transaction initiation timestamp. |
| `updated_at` | `TIMESTAMP WITH TIME ZONE` | Not Null | Transaction state update timestamp. |

### Redis In-Memory Architecture & Design

Redis is used in the payment module to intercept rapid duplicate payment button clicks in memory before making external HTTP network calls to Stripe.

#### 1. Key Naming Scheme & Data Types
* **Idempotency Lock Key:** `payment:idempotency:{idempotencyKey}`
* **Data Type:** String
* **Value:** Transaction processing status (`"IN_PROGRESS"` or `"COMPLETED:{transactionId}"`).
* **TTL Policy:** 86400 seconds (24 hours).

#### 2. In-Memory Idempotency Workflow
1. When a user submits payment details, the request includes a unique `idempotencyKey` generated by the frontend.
2. The payment service performs an atomic `SETNX` on `payment:idempotency:{idempotencyKey}` in Redis RAM.
3. If the key already exists, the service blocks the duplicate payment request immediately and returns the stored result from the initial attempt without charging the buyer's credit card twice.

## 4. Interfaces & Event Contracts

### External REST Endpoints

| Method | Endpoint Path | Description | Access Level |
| :--- | :--- | :--- | :--- |
| `POST` | `/api/v1/payments/intent` | Create a Stripe PaymentIntent for an active hold | Public (With Hold Token) |
| `POST` | `/api/v1/payments/confirm` | Confirm payment execution with gateway credentials | Public |
| `POST` | `/api/v1/payments/webhook` | Asynchronous webhook receiver endpoint for Stripe event updates | Gateway Only (Signed) |

### Internal Module Facade (`PaymentFacade`)

Exposes synchronous Java methods for in-memory cross-module calls:

* **Payment Authorization Method:** Accepts `holdToken`, `idempotencyKey`, `amountCents`, and `paymentMethodId`. Executes payment verification against Stripe Test SDK and records `payment_transactions` record. Returns a `PaymentResultDTO`. Used by the `order` module during checkout.
* **Refund Execution Method:** Accepts `transactionReference` and `reason`. Issues a full refund via Stripe SDK if an order transaction fails post-payment.

### Domain Events

#### `PaymentSucceededEvent` (Internal Spring Event)
* **Trigger:** Published when Stripe confirms successful payment authorization (either via direct API response or webhook).
* **Payload Details:** Contains `transactionReference`, `holdToken`, `stripePaymentIntentId`, `amountCents`, `userSessionId`.
* **Purpose:** Triggers the `order` module to finalize order persistence and consume the seat hold.

#### `PaymentFailedEvent` (Internal Spring Event)
* **Trigger:** Published when payment is declined, times out, or fails authorization.
* **Payload Details:** Contains `transactionReference`, `holdToken`, `failureReason`, `timestamp`.
* **Purpose:** Triggers the `hold` module to immediately release reserved seats back to Redis RAM stock.

## 5. Concurrency Control, Failure Modes & Edge Cases

* **Stripe Idempotency Enforcement:** Passes the `Idempotency-Key` header in all Stripe SDK calls so that even if network timeouts cause duplicate retries, Stripe guarantees the customer is charged exactly once.
* **Gateway Downtime Resilience (Resilience4j):** Wraps external Stripe API calls in Resilience4j Circuit Breakers and Retries. Transient network drops retry automatically up to 3 times before failing gracefully.
* **Browser Disconnect Reconciliation (Webhooks):** If a user closes their browser tab right after entering payment details, the frontend HTTP response is lost, but Stripe still processes the charge. The Stripe webhook (`POST /api/v1/payments/webhook`) catches the `payment_intent.succeeded` event asynchronously, verifies the cryptographically signed webhook signature, and completes the order in the background.
* **Custom Domain Exception Handling:**

  * Card Declined / Insufficient Funds $ightarrow$ Throws `PaymentDeclinedException` (Mapped to HTTP 402 Payment Required).
  * Gateway Network Timeout $ightarrow$ Throws `PaymentGatewayUnavailableException` (Mapped to HTTP 503 Service Unavailable).
